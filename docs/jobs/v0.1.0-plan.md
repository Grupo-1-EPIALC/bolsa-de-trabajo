## 2. Alcance de `v0.1.0`

### Entra

1. **RF-11 / HU-11** — Una empresa crea, edita y cierra ofertas con:
   - requisitos `required`, `desired` y `excluding`;
   - nivel 1–5 por skill;
   - experiencia mínima y área;
   - educación e idiomas;
   - estado inicial `active`.
2. **RF-12 / HU-12** — Una empresa ve y gestiona sus búsquedas:
   - listado filtrable por estado (`active`, `closed`, `all`);
   - cerrar una oferta;
   - reabrir una oferta cerrada.
3. **Endpoints del PDF:**
   - `GET /api/v1/jobs`
   - `POST /api/v1/jobs`
   - `GET /api/v1/jobs/{id}`
   - `PATCH /api/v1/jobs/{id}`
   - `DELETE /api/v1/jobs/{id}` (cierra la oferta)
   - `GET /api/v1/companies/me/searches`
4. **Paginación** `?page&size`, con alias `limit` para matching/mcp-tools.
5. **Auth**:
   - JWT RS256 de auth-service validado localmente con el JWKS;
   - `X-Service-Token` para matching-service y mcp-tools;
   - `company_id` sale del `sub` del JWT, nunca del body.
6. **Evento `job.created`** hacia n8n (WF-02 / HU-17), best-effort y configurable.
7. **Persistencia PostgreSQL** en el schema `jobs`, detrás de un puerto `JobRepository`.
8. **Seed de demo** con las 12 ofertas ficticias (`job-001` a `job-012`) que ya usa matching.
9. **Tests** UT-JOBS-01/02 + dominio, aplicación, API, auth, repositorio y contrato.
10. **Contratos**:
    - `contracts/jobs_service.openapi.json`
    - `contracts/jobs_frontend.md`
    - `contracts/jobs_matching.md`

### No entra en `v0.1.0`

| Fuera de alcance | Motivo |
|---|---|
| Postulaciones, preguntas de screening y `application` completo | No hay RF/HU de postulación en el PDF; matching maneja el match, no la postulación |
| Pasantías (`internship`) y contratos de pasantía | El PDF no las pide para jobs; el bloque común las deja opcionales |
| `inclusive_hiring` | Dato sensible opcional; no hay RF/HU |
| Estados `draft`, `paused`, `expired` | AGENTS §4.3 fija `active|closed`; el PDF sólo pide activa/cerrada |
| Analíticas, logo de empresa, tamaño real de empresa | No hay RF/HU; auth-service no expone logo ni tamaño |
| Filtros avanzados por ubicación, modalidad o texto | El PDF sólo pide filtro por estado; se agregan después de la demo |
| Migraciones Alembic | Se usa `create_all` en `v0.1.0`; Alembic queda para después de la demo |
| Cambios en frontend, profile-service, matching-service, mcp-tools, n8n o gateway | Cada uno tiene dueño; se coordinan por contrato |

## 4. Modelo de datos

Se implementa `JobOpportunity` de `contracts/estructura_comun_perfil_oferta_match.md` §6, con los bloques que el PDF exige y los opcionales que ya estaban definidos.

### Núcleo

| Campo | Tipo | Regla |
|---|---|---|
| `id` | string | `job-001` para seed; UUID para nuevas |
| `company_id` | string | `sub` del JWT de la empresa |
| `company_snapshot` | objeto | `{name, industry, size?, logo_url?}`; se obtiene de auth-service |
| `status` | `active \| closed` | creada `active`; `DELETE` la pasa a `closed` |
| `title` | string | obligatorio, 1–200 |
| `description` | string | obligatorio, 1–20000 |
| `responsibilities` | string[] | opcional, por defecto `[]` |
| `area` | string | opcional, por defecto `""` |
| `seniority` | enum | `no_experience \| trainee \| junior \| semi_senior \| senior` |
| `vacancies` | int | ≥ 1, por defecto 1 |
| `location` | objeto | `country`, `province`, `city` obligatorios |
| `work_conditions` | objeto | ver abajo |
| `requirements` | objeto | ver abajo |
| `benefits` | string[] | opcional, por defecto `[]` |
| `created_at`, `updated_at` | datetime | UTC |
| `published_at` | datetime | al crear y al reabrir |
| `expires_at` | datetime? | opcional; si viene, debe ser futuro |
| `version` | int | 1 al crear; +1 en cada edición, cierre o reapertura |

### `work_conditions`

Se reutiliza el bloque común §4.3, con los campos que aplican a una oferta:

`work_schedule[]`, `work_modality[]`, `hybrid_onsite_days`, `employment_type[]`, `contract_duration[]`, `weekly_hours {min,max}`, `shifts[]`, `availability_start`, `salary`, `relocation_support`, `travel_availability`, `driver_license[]`, `own_vehicle`, `own_equipment`, `invoicing_status`, `work_authorization[]`, `timezone`, `timezone_overlap_hours`.

`salary` usa `SalaryRange` del bloque común §4.2: `min`, `max`, `currency`, `period`, `gross`, `payment_mode`, `negotiable`, `adjustment`, `variable_compensation[]`, `visibility`, `to_agree`, `notes`.

### `requirements`

- `skills[]`: `{name, normalized, level 1–5, kind, years?, category?}`
- `languages[]`: `{name, normalized, level, kind, certification?}`
- `education[]`: `{institution?, degree?, field?, level, status, progress_percent?, gpa?, kind}`
- `experience`: `{min_years ≥ 0, area?, kind}`
- `certifications[]`: `{name, kind}`
- `academic?`: `{min_progress_percent?, careers[], min_current_year?}`

Regla dura: **al menos una skill `required`** (UT-JOBS-01).

### Persistencia

Tabla `jobs` en el schema `jobs`:

- columnas escalares para `id`, `company_id`, `status`, `title`, `description`, `area`, `seniority`, `vacancies`, `created_at`, `updated_at`, `published_at`, `expires_at`, `version`;
- columnas JSON para `company_snapshot`, `location`, `work_conditions`, `requirements`, `responsibilities` y `benefits`;
- índices por `status`, `company_id` y `published_at`.

El schema y el rol ya existen en `infra/postgres/init/01-schemas.sh`. `DATABASE_URL` ya llega desde `docker-compose.yml`. El servicio normaliza `postgresql://` a `postgresql+psycopg://`.

`v0.1.0` crea las tablas con `Base.metadata.create_all` al arrancar. No hay Alembic en esta entrega; se documenta como deuda técnica.

## 5. Endpoints y reglas

| Método | Ruta | Rol | Respuesta |
|---|---|---|---|
| `GET` | `/health` | público | `200 {status, service, version}` |
| `GET` | `/api/v1/jobs` | student/company/admin/service | `200 JobList` |
| `POST` | `/api/v1/jobs` | company | `201 JobOpportunity` |
| `GET` | `/api/v1/jobs/{id}` | autenticado | `200 JobOpportunity` |
| `PATCH` | `/api/v1/jobs/{id}` | company dueña | `200 JobOpportunity` |
| `DELETE` | `/api/v1/jobs/{id}` | company dueña | `204` |
| `GET` | `/api/v1/companies/me/searches` | company | `200 JobList` |

### Listado `GET /api/v1/jobs`

- `status`: `active` (default), `closed`, `all`. `student` y `company` sólo pueden pedir `active`; `admin` y service pueden pedir cualquiera.
- `page`: 1-based, default 1.
- `size`: 1–200, default 5.
- `limit`: alias de `size` para matching/mcp-tools. Si viene, gana sobre `size`.
- Orden: `published_at DESC`, `id ASC`.
- Respuesta: `{items, total, page, size, pages}` con objetos completos.

### Detalle

- Oferta activa: visible para cualquier autenticado.
- Oferta cerrada: visible sólo para la empresa dueña, `admin` o service token. Para el resto: `404`.

### Creación

- Sólo `company`.
- `company_id = sub` del JWT.
- `status = active`, `published_at = now`, `version = 1`.
- `company_snapshot` se obtiene de `GET /api/v1/auth/me` con el Bearer de la empresa: `name = legal_name`, `industry = activity`.
- Después de guardar se publica `job.created` a n8n. Si n8n no responde, se loguea y el alta no falla.
- No se aceptan `company_id`, `status`, `version`, `created_at`, `updated_at`, `published_at` ni `company_snapshot` en el body.

### Edición `PATCH`

- Sólo la empresa dueña. Otra empresa → **403** (UT-JOBS-02).
- Los bloques enviados se reemplazan completos; no hay merge profundo.
- Cada edición incrementa `version` y actualiza `updated_at`. La escritura persiste sólo si la
  `version` guardada sigue siendo la que se leyó; si no, responde `409 CONFLICT` y el cliente
  relee la oferta (lock optimista, evita perder un cambio entre dos ediciones simultáneas).
- `status` sólo acepta `active` y sólo se usa para **reabrir** una oferta `closed`.
- Cerrar se hace con `DELETE`, no con `PATCH`.

### Cierre `DELETE`

- Sólo la empresa dueña. Otra empresa → **403**.
- Pasa `status` a `closed`, actualiza `updated_at` y suma `version`.
- Si ya estaba cerrada, responde `204` sin cambios (idempotente).
- No se borra físicamente.

### `GET /api/v1/companies/me/searches`

- Sólo `company`.
- `status`: `active` (default), `closed`, `all`.
- `page`/`size`/`limit` igual que el listado.
- Devuelve sólo ofertas de `company_id = sub`.

### Sueldo y privacidad

- `public`: visible para todos.
- `on_match` o `hidden`: para estudiantes y otras empresas se devuelve `work_conditions.salary = null`.
- La empresa dueña, `admin` y service token ven el sueldo completo.
- Matching recibe el sueldo completo con service token y aplica su propia regla de `visibility`.

### Errores

Formato único:

```json
{"error": {"code": "NOT_FOUND", "message": "Oferta 'job-999' no encontrada", "details": {"job_id": "job-999"}}}
```

| HTTP | `code` | Cuándo |
|---|---|---|
| 401 | `UNAUTHORIZED` | Sin token, token inválido o expirado |
| 403 | `FORBIDDEN` | Rol incorrecto o recurso de otra empresa |
| 404 | `NOT_FOUND` | Oferta inexistente o cerrada para un tercero |
| 409 | `CONFLICT` | Otra escritura superó la `version` leída mientras se editaba/cerraba (lock optimista) |
| 422 | `INVALID_INPUT` | Body/query inválido (Pydantic) o regla de negocio violada, incluido UT-JOBS-01 |
| 502 | `UPSTREAM_ERROR` | auth-service o n8n no respondieron |

No se devuelven respuestas `400`: Pydantic y las reglas de negocio comparten el `422 INVALID_INPUT`.

## 6. Autenticación

- **Usuarios:** `Authorization: Bearer <access_token>`.
- **Servicios:** `X-Service-Token`. Nunca se acepta como Bearer.
- JWT RS256 validado contra `JWKS_URL`; se verifican `iss`, `aud`, `exp`, `sub` y `role`.
- Roles: `student`, `company`, `admin`, `service`.
- El gateway borra `X-Service-Token` en peticiones externas; aun así el servicio lo valida en tiempo constante.
- `company_id` siempre sale del `sub`, nunca del body.
- Recurso de otra empresa: **403** (AGENTS §4.3 y UT-JOBS-02).

## 7. Evento `job.created`

- Puerto `EventPublisher` en dominio.
- Adaptador `HttpN8nEventPublisher` que hace `POST {N8N_WEBHOOK_BASE_URL}/job-created`.
- Payload:

```json
{
  "event": "job.created",
  "occurred_at": "2026-11-05T14:00:00Z",
  "job_id": "job-013",
  "company_id": "uuid",
  "title": "Desarrollador/a Backend",
  "status": "active"
}
```

- Header `X-Service-Token` con el token interno.
- Timeout corto (3 s), best-effort: si falla, se loguea y el alta responde `201`.
- **Dependencia:** WF-02 no existe todavía en `n8n/workflows/`. El evento se emite igual; el workflow lo debe crear el dueño de n8n.

## 8. Tests

### Obligatorios del PDF

| ID | Caso | Resultado |
|---|---|---|
| UT-JOBS-01 | Crear oferta sin requisitos obligatorios | `422` |
| UT-JOBS-02 | Editar oferta de otra empresa | `403` |

### Agregados por AGENTS/DoD

- Dominio:
  - nivel de skill fuera de 1–5 → error;
  - `vacancies < 1` → error;
  - `salary.min > salary.max` → error;
  - `weekly_hours.min > weekly_hours.max` → error;
  - cierre idempotente;
  - reapertura sólo desde `closed`;
  - `version` incrementa;
  - sueldo oculto para terceros;
  - oferta cerrada oculta para estudiantes.
- Aplicación:
  - `company_id` sale del `sub`;
  - `company_snapshot` sale de auth;
  - `job.created` se publica sólo al crear;
  - listado paginado y filtrado por estado;
  - `/companies/me/searches` sólo devuelve ofertas propias.
- API:
  - 401 sin token / token inválido;
  - 403 estudiante creando;
  - 403 otra empresa editando/cerrando;
  - 404 oferta inexistente;
  - 201 creación;
  - 200 detalle/edición;
  - 204 cierre;
  - contrato de respuesta.
- Repositorio:
  - round-trip SQLite de todos los bloques;
  - actualización de `version`;
  - listado por estado y empresa.
- Contrato:
  - el OpenAPI contiene las rutas y schemas;
  - el seed cumple las reglas;
  - el seed trae los campos que espera `JobMapper`.

Cobertura ≥ 70 % en `domain/` y `application/` (configurado en `pyproject.toml`).
